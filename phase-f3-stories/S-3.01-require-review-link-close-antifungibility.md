# S-3.01: Delta — require-review Hook Link+Close Anti-Fungibility (BC-3.01.001 v1.25)

## Narrative

- **As a** CI/CD pipeline
- **I want** the require-review hook to enforce anti-fungibility between link
  markers and close markers (D-020/D-021), so that a link marker cannot be
  consumed by a close command and vice versa
- **So that** the strict write-block prevents unauthorized fungibility between
  these action types and maintains auditability of all Jira lifecycle transitions

## Behavioral Contracts

| BC | Title | Version |
|----|-------|---------|
| BC-3.01.001 | require-review Hook — Jira Field-Modification Gate | v1.25 |

## Acceptance Criteria

### Write-Block Extensions (D-020/D-021)

### AC-001 (traces to BC-3.01.001 delta — D-020 link anti-fungibility; VP-HOOK-033 consumer leg)
The hook's write-block must include `jr issue link ` and `--output json issue link `
as blocked patterns. The total write-block entries after this delta is 12 (up from
10 in ≤v1.22 — `jr issue link` was added at v1.23, establishing exactly 12; v1.24
was annotation-only with no further entry changes). Any `jr issue link` command not
preceded by a valid link marker must be denied.
(VP-HOOK-033 consumer leg — write-block extension + STEP 6a anti-fungibility; verification-delta vd:625, D-020/SM-57/SM-58)

### AC-002 (traces to BC-3.01.001 delta — D-021 close anti-fungibility; VP-HOOK-035 consumer leg)
The hook must enforce STEP-6 exact-type matching for close commands: a close command
(`jr issue move`) may only be authorized by a marker with `ticket_action_type = ["close"]`
(exactly). NOTE: `jr issue move` is ALREADY write-blocked (BC-3.01.001 L116, pre-delta);
the D-021 delta adds ONLY the STEP-6 exact-type `["close"]` binding — no new close
write-block entries are added by this delta. This ensures anti-fungibility: a link marker
or create-review marker cannot authorize a close command.
(VP-HOOK-035 consumer leg — STEP-6 close exact-type `["close"]` binding; verification-delta
vd:626-627, D-021; NOTE: SM-61/SM-62/SM-64 are S-3.02 EMITTER kills (disposition-guard
`hooks/disposition-guard/`) and are NOT killed by this consumer AC — they mutate the
close-scope hard-floor bypass, kill-switch gate, and close ticket_id charset at the EMITTER;
the SM-63 consume-time kill (close-state-token-allowlist-removed — require-review CONSUMER
STEP-6 command_pattern allowlist binding) is at AC-010 of this story; `jr issue move` was
already write-blocked pre-delta per BC-3.01.001 L116; delta = STEP-6 type binding only)

### AC-003 (traces to BC-3.01.001 EC-026 — link anti-fungibility test case)
A `jr issue link KEY1 KEY2` command (two positional keys; default "Relates" link-type;
no interposed link-type token — command_pattern `^jr (--output json )?issue link <KEY1> <KEY2>( |$)`)
without a corresponding link marker in the marker directory must be DENIED. The deny must not be
overridden by an existing non-link marker (e.g., a create-review or close marker
cannot authorize a link command).
(BC-3.01.001 ~L115 anchored command_pattern; EC-026 vectors use `jr issue link SEC-123 SEC-456`
with two positional keys, default Relates link-type, NO interposed link-type token.)

### AC-004 (traces to BC-3.01.001 EC-027 — close anti-fungibility test case)
A `jr issue move` (close) command without a corresponding close marker
must be DENIED. A link marker must not authorize a close command.

### STEP 6 Exact-Type Matching

### AC-005 (traces to BC-3.01.001 delta — STEP 6 exact-type matching for link)
At STEP 6, when the command is a link command, the hook must match ONLY against
markers with `ticket_action_type = ["link"]` (exactly). A `comment-review` marker,
a `create-review` marker, a `close` marker, etc. must NOT authorize a link command.

### AC-006 (traces to BC-3.01.001 delta — STEP 6 exact-type matching for close)
At STEP 6, when the command is a move command, the hook must match ONLY
against markers with `ticket_action_type = ["close"]` (exactly). A `link` marker
or any non-close marker must NOT authorize a close command.

### AC-007 (traces to BC-3.01.001 invariant — marker iterative-consume with POSIX atomic rename)
The Phase 2 marker consumption algorithm uses iterative POSIX atomic rename (mv)
to consume markers. A marker consumed for a link command must not remain available
to authorize a second link command. Each marker is single-use. (D-DEC-001)

### AC-008 (traces to BC-3.01.001 invariant — link marker ≠ close marker ≠ create marker)
Link markers, close markers, create-review markers, and comment-review markers are
not interchangeable. The STEP 6 exact-type matching must enforce this at
hook runtime.

### AC-009 (traces to BC-3.01.001 EC-026/EC-027 — regression: existing non-link/close markers unaffected)
Existing tests for create-review, comment-review, and regular create/comment/assign
marker flows must continue to pass after this delta. The delta adds new deny paths
but must not break existing authorized paths.

### STEP 6 Close-State Allowlist Binding (Consumer-Side)

### AC-010 (traces to BC-3.01.001 STEP 6 exact-type matching — close command_pattern allowlist binding; VP-HOOK-035 consumer SM-63 kill)
At STEP 6, when consuming a `["close"]` marker, the hook's command_pattern for close
is bound to the `CLOSE_STATE_ALLOWLIST={Done,Closed,Resolved}` (config-validated at
setup time via BC-6.01.001/BC-6.01.003). Two assertions:

**(a) Non-allowlisted state → DENY:** A valid `["close"]` marker + a `jr issue move SEC-42 WontFix`
command (WontFix ∉ CLOSE_STATE_ALLOWLIST) → require-review DENIES. The close command_pattern
restricts the second argument of `jr issue move` to the allowlisted states only; `WontFix` does
not match → DENY (marker NOT consumed).

**(b) Allowlisted state → ALLOW:** A valid `["close"]` marker + a `jr issue move SEC-42 Done`
command (Done ∈ CLOSE_STATE_ALLOWLIST) → require-review ALLOWS; marker consumed atomically.

This kills SM-63 (close-state-token-allowlist-removed, ADV-F2-P18-005): under SM-63 the
command_pattern accepts any second argument to `jr issue move` → the non-allowlisted `WontFix`
is wrongly authorized and the DENY assertion fails → the mutant dies. Note: `jira_close_state`
is config-side (not verdict-influenceable), so this is a pattern-binding regression, not an
LLM-injection surface. DISTINCT from SM-67 (disposition-guard EMIT-time re-check at a different
site/time — SM-67 is killed at S-3.02 via AC-002b/SM-67; SM-63 is the CONSUME-time binding
killed here at the consumer).
(VP-HOOK-035 consumer leg — SM-63 close-state-allowlist CONSUMER binding kill; verification-delta
~L1338, D-021/P18-005)
