# S-6.03: Delta — Activate Skill CLOSE_STATE_ALLOWLIST Setup-Time Validation (BC-6.01.001 v1.8)

## Narrative

- **As a** SecOps operator running `/activate`
- **I want** activation to validate `jira_close_state` against the
  CLOSE_STATE_ALLOWLIST = {"Done", "Closed", "Resolved"} at setup time
- **So that** the monitoring-loop never silently accepts an invalid close state
  that would prevent correct Jira ticket lifecycle management

## Behavioral Contracts

| BC | Title | Version |
|----|-------|---------|
| BC-6.01.001 | activate Skill — Per-Project Activation Lifecycle with Prism MCP Integration | v1.8 |

## Acceptance Criteria

### AC-001 (traces to BC-6.01.001 postcondition PC#13 — setup-time validation)
During `/activate`, after the user provides `jira_close_state`, the skill validates
the value against `CLOSE_STATE_ALLOWLIST = {"Done", "Closed", "Resolved"}`. If the
value is outside the allowlist, activation FAILS EARLY with an explicit error
message before writing any config. (P18-005)

### AC-002 (traces to BC-6.01.001 EC-015 — invalid close state)
If `jira_close_state` is not in `{"Done", "Closed", "Resolved"}`, the skill emits:
"jira_close_state '<value>' is not valid. Allowed values: Done, Closed, Resolved."
Activation must not proceed and must not write a prism.toml or activate.toml with
an invalid close state.

### AC-003 (traces to BC-6.01.001 invariant — CONFIG-driven, not verdict-influenceable)
`CLOSE_STATE_ALLOWLIST` must be enforced at setup time only — it is NOT read during
monitoring-loop runtime from user-supplied verdict fields. The allowlist check must
be in the activation code path, not in any verdict evaluation path. This prevents
LLM injection via verdict content. (D-021)

### AC-004 (traces to BC-6.01.001 invariant — valid values pass through)
When `jira_close_state` is "Done", "Closed", or "Resolved", activation proceeds
normally without any additional warnings about the close state.

### AC-005 (traces to BC-6.01.001 invariant — case sensitivity)
The allowlist check is case-sensitive. "done", "DONE", "closed" are NOT valid;
only the exact strings "Done", "Closed", "Resolved" are accepted.

### AC-006 (traces to BC-6.01.001 EC-015 — zero LLM injection surface)
The CLOSE_STATE_ALLOWLIST validation must use an exact-match against a hardcoded
constant set. The set must not be derived from user input, environment variables
(except those set at activation time and stored immutably), or verdict fields.

### AC-007 — VP-SKILL-076 activate leg (traces to BC-6.01.001 PC#12/EC-014 — setup-time jira_project_key charset validation)
During `/activate`, any `jira_project_key` value provided by the operator MUST be
validated against `^[A-Z][A-Z0-9]+$` at setup time before any config is written.
A key containing a hyphen (e.g., `PRISM-DEMO`), lowercase letters, or special
characters MUST be rejected with an explicit user-facing error:
"Invalid Jira project key '<X>': Jira project keys must be uppercase alphanumeric
with no hyphens or spaces — e.g., PRISMDEMO, SEC, SECOPS."
Activation MUST refuse to complete until a conformant key is provided.
Rationale: a non-conformant key causes PROJECT-KEY-CHARSET-DENY fail-closed drops
on every marker issuance at disposition-guard (BC-3.03.001 P12-001/O7).
BATS test `activate validates jira_project_key charset at setup time (VP-SKILL-076
activate leg)` must pass.
(BC-6.01.001 PC#12/EC-014; D-DEC-008; P13-002 CRITICAL; VP-SKILL-076 activate leg; SM-54 kill — behavioral activate leg)
