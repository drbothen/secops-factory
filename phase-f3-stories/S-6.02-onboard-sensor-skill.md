# S-6.02: Implement onboard-sensor Skill (BC-6.01.004 v1.1)

## Narrative

- **As a** SecOps operator
- **I want to** run `/onboard-sensor <org_slug> <sensor_id>` to add a new sensor overlay
  for an existing customer org with credential walkthrough via the AD-017 piped-stdin pattern
- **So that** the monitoring-loop can query that sensor's data through prism with verified
  end-to-end connectivity

## Behavioral Contracts

| BC | Title | Version |
|----|-------|---------|
| BC-6.01.004 | onboard-sensor Skill — Sensor Overlay TOML Write, AD-017 Credential Walkthrough, and SELECT 1 Verification | v1.1 |

## Acceptance Criteria

### AC-001 (traces to BC-6.01.004 postcondition 1)
A file `<spec_dir>/customers/<org_slug>/<sensor_id>.sensor.toml` is written with at
minimum: `extends`, `instance_id`, and `base_url` fields before the skill reports
success.

### AC-002 (traces to BC-6.01.004 invariant 1 — AD-017 piped-stdin)
The skill provides the exact `echo "<credential_value>" | prism --config-dir <dir>
credential set --sensor <sensor_id> --name <credential_name> --org-slug <org_slug>`
command template for the user to run in their terminal. The skill must not execute
`prism credential set` on the user's behalf, and must not request credential values
in chat.

### AC-003 (traces to BC-6.01.004 invariant 2 — prism_describe verification)
After the user confirms running the credential command, the skill verifies via
`prism_describe` (not by re-reading the credential) that the sensor appears in the
prism MCP response. Success is conditional on this check passing.

### AC-004 (traces to BC-6.01.004 invariant 3 — SELECT 1 mandatory)
The skill executes a `SELECT 1` query via the prism `query` MCP tool against the
newly onboarded sensor's table. The skill reports success only if `SELECT 1` returns
a non-error response. A silent or error response must be reported as a failure.

### AC-005 (traces to BC-6.01.004 invariant 4 — --config-dir isolation)
The credential set command template provided to the user must include `--config-dir
<dir>` pointing to the customer's config directory. The template must not default to
the global config dir.

### AC-006 (traces to BC-6.01.004 invariant 5 — supported sensor IDs)
The skill rejects any `sensor_id` not in `{crowdstrike, armis, claroty, cyberint}`
with a clear error message listing the four supported values. V1 scope per D-033:
Claroty-xDome is the target, but all 4 sensors must be accepted.

### AC-007 (traces to BC-6.01.004 precondition — org must exist)
If `org_slug` is not registered in `prism.toml`, the skill stops with "Org
'<org_slug>' not found in prism.toml. Run onboard-customer first." (EC-001).

### AC-008 (traces to BC-6.01.004 invariant 6 — announce at start)
The skill emits "I am using the onboard-sensor skill…" as its first output,
before any file operation.

### AC-009 (traces to BC-6.01.004 postcondition 5 — fail-loud on verification failure)
If `prism_describe` does not show the sensor (EC-004), the skill reports "Sensor
<sensor_id> not visible in prism_describe for org <org_slug>. Check credential with:
prism credential list --org-slug <org_slug>" and does NOT emit a success message.

### AC-010 (traces to BC-6.01.004 EC-005 — SELECT 1 error)
If `SELECT 1` returns an error response, the skill reports connectivity failure with
the raw error, suggests checking base_url, network access, and credential success,
and does NOT emit a success message.

### AC-011 (traces to BC-6.01.004 EC-006 — in-chat credential paste)
If the user pastes a credential value directly in chat, the skill immediately
declines to process it, reminds the user of the piped-stdin pattern, and does not
echo or store the value.

### AC-012 (traces to BC-6.01.004 EC-007 — missing base_url)
If `base_url` is missing or empty, the skill prompts for it before writing
`sensor.toml`; it does not write a sensor.toml with an empty base_url field.

### AC-013 — VP-SKILL-054 (traces to BC-6.01.004 verification property VP-SKILL-054)
The SKILL.md text never contains a pattern requesting credential value paste in
chat; only the piped-stdin `echo | prism credential set` pattern is documented.
BATS test `onboard-sensor AD-017 piped-stdin pattern documented in SKILL.md` must
pass.

### AC-014 — VP-SKILL-055 (traces to BC-6.01.004 verification property VP-SKILL-055)
The SKILL.md workflow step for SELECT 1 verification is present; success message
section is gated after SELECT 1 step. BATS test `onboard-sensor has SELECT 1
verification step` must pass.

### AC-015 (traces to BC-6.01.004 invariant 1 — AD-017 credential-set.ps1 Windows parity; handoff-brief §6)
`skills/onboard-sensor/credential-set.ps1` EXISTS and enforces the same AD-017
piped-stdin / `--config-dir` template as `credential-set.sh`. Structural grep parity
assertions:

**(a) Piped-stdin pattern present:** `.ps1` contains a PowerShell-equivalent piped-stdin
credential command (e.g. `Write-Output`/pipe form of
`echo "<credential_value>" | prism --config-dir <dir> credential set ...`).
Structural grep: `Select-String -Pattern 'credential set'` (or `grep -i 'credential set'`)
returns ≥ 1 match in `credential-set.ps1`.

**(b) `--config-dir` flag present:** `.ps1` contains `--config-dir` in the credential
command template, ensuring per-customer config-dir isolation (AD-017 invariant).
Structural grep: `Select-String -Pattern '\-\-config-dir'` returns ≥ 1 match.

**(c) No in-chat credential request:** `.ps1` does NOT prompt for or echo credential
values in a pattern that would expose them; it follows the same pipe-only discipline
as `credential-set.sh`.

Parity rationale: handoff-brief §6 mandates every `.sh` helper has a companion `.ps1`
on Windows-capable releases (D-DEC-010 packaging). Parallel to S-10.02 AC-019
(run-monitoring-loop.ps1 precondition-gate parity). Points unchanged — the .ps1 parity
work is included in the 5-point estimate for this story.
(BC-6.01.004 invariant 1; architecture-delta §D-DEC-010 Windows parity; handoff-brief §6)
