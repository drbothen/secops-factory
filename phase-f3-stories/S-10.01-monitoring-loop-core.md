# S-10.01: Implement monitoring-loop Core Pipeline (BC-10.01.001 v1.36 — Stages 0-8, ICD-203, Hard-Floor, Kill-Switch)

## Narrative

- **As a** SecOps autonomous triage system
- **I want** the monitoring-loop skill to execute a 9-stage (Stages 0-8) alert triage
  pipeline producing an 18-field ICD-203 defensible verdict for each ingested alert
- **So that** every alert is triaged consistently with hard-floor routing, kill-switch
  controls, and audit-traceable decisions that can be reviewed by human operators

## Behavioral Contracts

| BC | Title | Version |
|----|-------|---------|
| BC-10.01.001 | Autonomous Scheduled Tier-1 Alert Triage with ICD-203 Defensible Records | v1.36 |

## Acceptance Criteria

### Stage Pipeline Correctness

### AC-001 (traces to BC-10.01.001 precondition — Stage 0 sensor health)
Stage 0 checks sensor health status before processing alerts. If sensor_health_status
is `silent` or `degraded`, disposition is forced to `Indeterminate-due-to-missing-
telemetry`; a restricted review marker (`create-review` or `comment-review`) is
issued EXEMPT from the autonomy_enabled kill switch.

### AC-002 (traces to BC-10.01.001 postcondition — 18-field ICD-203 verdict)
Every processed alert produces a verdict with all 18 ICD-203 fields populated:
(1) disposition, (2) confidence, (3) sensor_health_status, (4) evidence_artifacts,
(5) timeline_events, (6) hypotheses_considered, (7) alternatives_rejected,
(8) uncertainty_explicit, (9) attack_techniques, (10) agent_actions,
(11) human_actions, (12) tuning_signal, (13) severity, (14) asset_type,
(15) ticket_action_type, (16) native_severity, (17) sensor_family,
(18) scored_priority. A verdict missing any field is a defect.
(BC-10.01.001 Invariant #9: field 11 = `human_actions` array of {ts_utc, actor_id,
action}; field 12 = `tuning_signal` {rule_id, asset, reason} or null — null for
TP/Indeterminate; required non-null for FP/BTP.)
Additionally, every entry in `agent_actions` (field 10) MUST carry an
automation-boundary annotation of exactly one of: `auto`, `propose-only`, or
`requires-human-approval` (BC-10.01.001 postcondition #5). An `agent_actions`
entry without this annotation is a defect.

### AC-003 (traces to BC-10.01.001 postcondition — Stage 1 NORMALIZE_SEVERITY)
Stage 1 sets `verdict.severity` (field 13) via `NORMALIZE_SEVERITY(native_severity,
sensor_family)` using the D-DEC-013 deterministic table. The loop also writes
`native_severity` (field 16) and `sensor_family` (field 17) — the disposition-guard
hook cross-validates SEVERITY-MISMATCH at STEP 1a.

### AC-004 (traces to BC-10.01.001 postcondition — Stage 5 assess-priority)
Stage 5 calls the `assess-priority` skill (BC-4.05.001) and writes the result to
`verdict.scored_priority` (field 18). The severity floor in Stage 6 (DISPOSE) hard-floor check
keys on field 18 (scored_priority), NOT on field 13 (severity). (P11-002)

### Hard-Floor and Kill-Switch

### AC-005 (traces to BC-10.01.001 Invariant #10 / §3.9 — hard-floor categories)
When any hard-floor condition applies, `ticket_action_type` (field 15) must be set
to `create-review` or `comment-review`. Hard-floor conditions:
(a) `disposition == Indeterminate`,
(b) `verdict.scored_priority in {HIGH, CRIT}`,
(c) `verdict.asset_type in CRITICAL_ASSET_TYPES ∪ {unknown}` (ADV-F2-P2-010),
(d) `verdict.attack_techniques` contains T1003/T1068/T1021/T1041,
(e) `verdict.sensor_health_status in {degraded, silent}`.
Setting `ticket_action_type = "none"` for a hard-floor verdict is a defect.
(D-DEC-012 fail-loud invariant)

### AC-006 (traces to BC-10.01.001 invariant — unknown asset_type conservative floor)
A verdict with `severity=LOW` + `asset_type=unknown` + benign technique
(`scored_priority` any value) must route to `create-review` or `comment-review`
(ADV-F2-P2-010 ORCHESTRATOR POLICY DECISION). It must NOT receive a regular
marker or be silent. (VP-HOOK-026 unknown-asset leg)
**Loop-side end-to-end CO-GUARD for SM-29 — the discriminating emitter kill for
SM-29 is at S-3.02 AC-017 (disposition-guard, the build-capable owner); this AC is
the loop-side integration guard only.**

### AC-007 (traces to BC-10.01.001 invariant 11 — autonomy_enabled kill switch)
When `autonomy_enabled=false`, ZERO REGULAR (non-review) Jira markers are issued
and ZERO regular `jr issue comment/create/assign/link/close` calls are made.
`link` and `close` are REGULAR scope when `hard_floor_applies()`=FALSE
(D-028/P23-003 extension — BC-10.01.001 v1.36 Invariant #11 / VP-SKILL-065 v1.25).
Evidence collection, verdict construction, and Jira drafting continue unaffected.
Exceptions (EXEMPT from kill switch per VP-SKILL-065 v1.25/P23-003):
(a) `create-review` and `comment-review` for genuine hard-floor verdicts
(`hard_floor_applies()=TRUE`) still execute regardless of `autonomy_enabled`
(D-DEC-012 Option A);
(b) A hard-floor link verdict (`hard_floor_applies()=TRUE` +
`ticket_action_type=link`) routes via disposition-guard STEP 3b → null-binding
guards pass → EMIT_LINK_MARKER true (P24-001 positional) → `["link"]` marker
issued REGARDLESS of `autonomy_enabled` (EXEMPT per D-027/D-028, mirrors D-DEC-012
Option A review-class exemption). (VP-SKILL-065)

### AC-008 (traces to BC-10.01.001 postcondition — ADV-F2-P7-001 Stage-8 Iron Law)
When `ticket_action_type = "create-review"`, the Stage-8 `jr` command must be:
`jr [--output json] issue create --project ${JIRA_PROJECT_KEY} --label
(REVIEW-REQUIRED|BLIND-SPOT)` with `--project` FIRST flag and `--label` SECOND
flag. No flags interposed between them. Mis-ordered label → DENY at require-review
consumer STEP 5.

### AC-009 (traces to BC-10.01.001 postcondition — STEP 4 DENY-THE-WRITE)
If disposition-guard returns `HARD-FLOOR-UNDER-LABEL` (under-labeled verdict),
the loop re-issues the verdict Write with `ticket_action_type` set to the corrective
review token from the deny reason. After 3 consecutive `HARD-FLOOR-UNBINDABLE`
denies for the same verdict, the loop emits `HARD-FLOOR-LIVELOCK-ABORT` and
advances to the next verdict. (P9-008 OBS)

### Ticket Routing Edge Cases (BC-10.01.001 EC-007 through EC-022)

### AC-018 (traces to BC-10.01.001 EC-007 — open BLIND-SPOT ticket exists)
When Stage 0 detects sensor silence (EC-006 BLIND-SPOT path) and an open BLIND-SPOT
ticket already exists for `(org_slug, sensor_id)`, the loop appends a comment to the
existing ticket (`ticket_action_type = "comment-review"`). It does NOT create a new
BLIND-SPOT ticket. D-DEC-004 one-open-per-org-sensor invariant enforced.
(VP-SKILL-068 comment-not-create leg — test MUST assert `ticket_action_type="comment-review"` and zero `jr issue create` calls when open BLIND-SPOT ticket exists; this is distinct from the VP-SKILL-068 dedup/null-ticket_id fallback leg at AC-010.)

### AC-019 (traces to BC-10.01.001 EC-008 — closed BLIND-SPOT ticket exists, D-022; VP-HOOK-036 compound-write)

`(org_slug, sensor_id)` is CLOSED, the loop issues TWO sequential verdict Writes
per D-022:
- verdict-1: `ticket_action_type=create-review`, `jira_project_key=...` → Stage 8
  `jr issue create --project ${JIRA_PROJECT_KEY} --label BLIND-SPOT` → returns NEW_KEY;
- verdict-2: `ticket_action_type=link`, `ticket_id=NEW_KEY`,
  `link_target_ticket_id=<closed_ticket_key>` → Stage 8 `jr issue link NEW_KEY <closed_key>`.
Iron Law (D-022): verdict-2 MUST NOT be written until verdict-1 `jr issue create` returns

(VP-HOOK-036 — compound two-sequential-verdict-Write; D-022 Iron Law; verification-delta vd:627)

`link_target_ticket_id=C`) to recover the missing structural link. Do NOT issue a plain
comment-only verdict for an orphan duplicate. If O is a hard-floor ticket,
D-027 applies at BC-3.03.001 STEP 3b: the link marker is issued exempt from kill switch.

### AC-024 — VP-SKILL-062 (traces to BC-10.01.001 EC-012 — propose-reopen draft; never-auto-reopen invariant)
When Stage 6 (DISPOSE) determines the root cause matches a RESOLVED ticket (loop-local EC-020 / BC EC-012),
the monitoring-loop DRAFTS a propose-only comment with:
- `annotation = "propose-only"` in `agent_actions` (ICD-203 field 10)
- A human-readable SLA statement (e.g., "SLA: reopen within 48h if evidence persists")
- `ticket_action_type = "comment-review"` (issues a review marker; does NOT execute reopen)
The loop does NOT execute a ticket reopen (`jr issue transition` or equivalent reopen command).
