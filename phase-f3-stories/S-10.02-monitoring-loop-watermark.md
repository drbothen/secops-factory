# S-10.02: Implement monitoring-loop Watermark and Late-Event Detection (BC-10.01.001 v1.36 — VALIDATE_WATERMARK_FOR_RUN, DETECT_LATE_EVENT, Cron Wrapper)

## Narrative

- **As a** scheduled monitoring-loop operator
- **I want** the monitoring-loop to maintain per-(org, sensor) watermarks with
  once-per-run RFC3339 validation and detect late-arriving events that predate
  the watermark
- **So that** the loop processes alerts incrementally without full-history rescans,
  correctly flags late events in the ICD-203 verdict, and surfaces watermark
  configuration errors through cron wrapper audit gates

| BC | Title | Version |
|----|-------|---------|
| BC-10.01.001 | Autonomous Scheduled Tier-1 Alert Triage with ICD-203 Defensible Records | v1.36 (watermark/late-event sections) |

## Acceptance Criteria

### VALIDATE_WATERMARK_FOR_RUN

### AC-001 (traces to BC-10.01.001 postcondition #2 / D-DEC-002 — watermark atomicity)
The watermark file is written atomically: write to a temp file first, then rename
(`mv -f`) to the final path. A partial write that crashes mid-operation must not
corrupt the stored watermark.

### AC-002 (traces to BC-10.01.001 postcondition — VALIDATE_WATERMARK_FOR_RUN once-per-run)
`VALIDATE_WATERMARK_FOR_RUN(org, sensor)` is called exactly ONCE per (org, sensor)
pair per monitoring-loop run — not once per alert, not once per stage. Calling it
more than once per run is a defect. (VP-SKILL-073 once-per-run cardinality, SM-82/83)

### AC-003 (traces to BC-10.01.001 postcondition — VALIDATE_WATERMARK_FOR_RUN validation logic; VP-SKILL-050 future-timestamp rejection)
On invocation:
(a) If no watermark file exists (first run) → 24h query lookback floor applied for INGEST
    (VP-SKILL-072, Invariant #13); sets `late_event_enabled=false` (DETECT_LATE_EVENT is a
    complete no-op for this run — writes nothing; no late_event_threshold set; no
    DETECT_LATE_EVENT_SUPPRESSED entry written). (BC-10.01.001 Invariant #14 Stage-1 ~L626;
    EC-023 ~L757; VP-SKILL-073 ~L797)
(b) If watermark file exists: parse RFC3339 timestamp; if invalid format OR
    timestamp is in the future → sets `late_event_enabled=false`; emits exactly
    ONE `DETECT_LATE_EVENT_SUPPRESSED` entry with reason=WATERMARK_INVALID
    (non-RFC3339) or reason=WATERMARK_FUTURE (future-dated); AND applies the 24h
    lookback PrismQL `_time` bound (`WHERE _time >= now() - INTERVAL 24 HOURS`)
    mirroring the first-run fallback (EC-001/AC-004/AC-010); continues (does not abort).
    (VP-SKILL-050 — future-timestamp rejection leg; EC-002/EC-003 24h-fallback;
    BC-10.01.001 EC-002/EC-003; verification-delta vd:684-685)
(c) If watermark file exists and timestamp is valid RFC3339 and not in the future →
    sets `late_event_enabled=true`, `late_event_threshold = stored_watermark`.

### AC-004 (traces to BC-10.01.001 invariant — first-run 24h lookback, VP-SKILL-072)
A loop-stub run against an EMPTY watermark dir MUST emit a PrismQL query bounded
to `now() - INTERVAL 24 HOURS` (never a full-history scan). After a successful run,
a watermark file is persisted at the latest processed `_time`. A control leg with
an existing watermark does NOT take the 24h branch.

### DETECT_LATE_EVENT

### AC-005 (traces to BC-10.01.001 postcondition — DETECT_LATE_EVENT per-event; VP-SKILL-073)
`DETECT_LATE_EVENT(event._time, stored_watermark)` is called per-event (not per-run).
When `late_event_enabled=false`, it is a NO-OP — no entry is written.
When `late_event_enabled=true` and `event._time < stored_watermark` (RAW watermark,
strictly-below; P40-001: boundary event._time == stored_watermark is NOT late), the
loop emits `LATE_EVENT_DETECTED` to `watermarks/audit.log`.
`WATERMARK_GRACE_SECONDS` is the query re-fetch-window floor (defines what events are
ingested), NOT the late-event comparator. The comparator is always the RAW stored_watermark.
(VP-SKILL-073 — raw watermark threshold; BC-10.01.001 EC-023, P40-001; distinct from
VP-SKILL-068 dedup invariant)

### AC-006 (traces to BC-10.01.001 EC-023 — LATE_EVENT_DETECTED; VP-SKILL-073)
When a late event is detected (`event._time < stored_watermark`, raw watermark,
strictly-below; P40-001 threshold), the monitoring-loop emits a `LATE_EVENT_DETECTED`
entry to `watermarks/audit.log` (fields: event_time, watermark, grace_window) for that
alert. The event is processed NORMALLY through all pipeline stages — it is NEVER
dropped. No pipeline stage is skipped or altered.
(BC-10.01.001 EC-023 — raw watermark threshold; VP-SKILL-073 primary leg)

### AC-007 (traces to BC-10.01.001 EC-024 — DETECT_LATE_EVENT_SUPPRESSED)
When `VALIDATE_WATERMARK_FOR_RUN` finds an invalid or future-dated watermark, it
emits exactly ONE `DETECT_LATE_EVENT_SUPPRESSED` entry to `watermarks/audit.log`
(the late-event audit log — NOT `markers/audit.log`, which records hook-enforcement
codes). No further DETECT_LATE_EVENT calls are made for that (org, sensor) in this run.

### Cron Wrapper

### AC-008 — VP-SKILL-075 Gate 1 (traces to BC-10.01.001 postcondition — cron wrapper Gate 1; VP-SKILL-075 operator-boundary)
The cron wrapper checks the monitoring-loop exit code and the `permission_denials`
field. If `is_error=true` OR `permission_denials` is non-empty, Gate 1 fails and
the wrapper emits a cron failure alert.
(VP-SKILL-075 — operator-boundary cron-exit-nonzero; Gate-1 `.permission_denials` leg; verification-delta vd:442)

### AC-009 — VP-SKILL-075 Gate 2 (traces to BC-10.01.001 postcondition #7 — cron wrapper Gate 2; VP-SKILL-075 operator-boundary)
The cron wrapper greps `${CLAUDE_PLUGIN_DATA}/markers/audit.log` (the hook
enforcement audit log; **NOT** `${CLAUDE_PLUGIN_DATA}/watermarks/audit.log` — that
is the late-event log recording `LATE_EVENT_DETECTED` / `DETECT_LATE_EVENT_SUPPRESSED`
entries; Gate 2 does NOT read the watermarks log) for any of the five hook enforcement
codes: `HARD-FLOOR-LIVELOCK-ABORT`, `HARD-FLOOR-UNBINDABLE`, `UNDER-LABEL-DENIED`,
`SEVERITY-MISMATCH`, `MARKER-WRITE-FAILED`. Any match fails Gate 2 and the wrapper
exits 1 even when `is_error=false` and `permission_denials==0`.
(BC-10.01.001 Postcondition #7 ~L176-193: `MARKERS_AUDIT="${CLAUDE_PLUGIN_DATA}/markers/audit.log"`;
VP-SKILL-075 — operator-boundary cron-exit-nonzero; Gate-2 markers/audit.log legs;
verification-delta vd:442)

**Positive-coverage assertion (required):** Seed `${CLAUDE_PLUGIN_DATA}/markers/audit.log`
with a line containing `HARD-FLOOR-LIVELOCK-ABORT` before invoking the cron wrapper
(with the monitoring-loop otherwise exiting 0 and `is_error=false`). Assert the
cron wrapper exits 1. This confirms Gate 2 correctly reads `markers/audit.log` and
cannot be silenced by pointing it at the watermarks log or an empty path.

### AC-010 — VP-SKILL-072 (traces to BC-10.01.001 VP-SKILL-072)
First-run 24h lookback correctness: loop-stub run against EMPTY watermark dir emits
PrismQL bounded to `now() - INTERVAL 24 HOURS`; after successful run, watermark
file is persisted; control leg with existing watermark does NOT take 24h branch.
FINALIZED per verification-delta v1.5 §7 Part E.

### AC-011 — VP-SKILL-073 (traces to BC-10.01.001 VP-SKILL-073 late-event detection correctness + cardinality addendum)

**PRIMARY leg (late-event detection correctness):** `DETECT_LATE_EVENT(event._time,
stored_watermark)` correctly identifies events strictly below the RAW stored watermark
and appends a `LATE_EVENT_DETECTED` audit entry to `watermarks/audit.log` WITHOUT
dropping the event or altering pipeline execution:
- `event._time < stored_watermark` (strictly-below) → appends LATE_EVENT_DETECTED audit entry
- `event._time == stored_watermark` (boundary) → NOT late; no audit entry
- `event._time > stored_watermark` → NOT late; no audit entry
- First run (no stored watermark) → `DETECT_LATE_EVENT` early return; no audit entry (false-positive prevention)
The event MUST proceed normally through all pipeline stages regardless of late-event detection.
BATS vectors per BC-10.01.001 VP-SKILL-073: `@test "monitoring-loop DETECT_LATE_EVENT:
event strictly below stored_watermark appends LATE_EVENT_DETECTED to watermarks/audit.log"`;
`@test "monitoring-loop DETECT_LATE_EVENT: event at-or-above stored_watermark does NOT
append to audit.log"`; `@test "monitoring-loop DETECT_LATE_EVENT first-run no watermark:
early return, no audit entry"`; `@test "monitoring-loop DETECT_LATE_EVENT: event is
processed normally through all pipeline stages regardless of late-event flag"`.

**ADDENDUM leg — v1.36 CARDINALITY (P43-002):** `VALIDATE_WATERMARK_FOR_RUN(org, sensor)`
is called exactly ONCE per (org, sensor) per run; a corrupt/future-dated watermark
produces exactly ONE `DETECT_LATE_EVENT_SUPPRESSED` entry regardless of event count.
SM-82 = `VALIDATE_WATERMARK_FOR_RUN()` moved back INSIDE the per-event loop (reverts to
per-event validation → N `DETECT_LATE_EVENT_SUPPRESSED` entries for N events);
SM-83 = `DETECT_LATE_EVENT()` retains its own inline watermark validation with the
`late_event_enabled` guard removed (per-event suppression flood restored). Both are
killed by a multi-event (N≥2) corrupt/invalid-watermark run asserting
`grep -c DETECT_LATE_EVENT_SUPPRESSED == 1` (exactly ONE suppressed entry);
the story BATS uses 50 events, exercised at the holdout layer by HS-047
(3 events) — both discriminate SM-82/SM-83. NOTE: the 50-event BATS run and the
3-event HS-047 holdout are distinct scenarios; HS-047 is NOT a 50-event run.
(verification-delta P43-002 §4 mutant catalog)

### AC-012 (traces to BC-10.01.001 postcondition #2 / D-DEC-002 — atomic watermark write regression guard)
Atomic watermark write verified: write-then-rename pattern confirmed; a mid-write
crash (simulated by test) does not leave a partial watermark at the final path.
(D-DEC-002 watermark atomicity; Postcondition #2; no dedicated VP in frozen roster — atomicity
is enforced by D-DEC-002/Postcondition-#2 cross-checked at AC-001 and AC-013)

### AC-013 — VP-SKILL-050 monotonicity primary leg (traces to BC-10.01.001 invariant 4 / D-DEC-002 — watermark never regresses; verification-delta vd:756)
The per-(org, sensor) watermark value written to disk after each successful run MUST be
≥ the previously persisted watermark value (the watermark never regresses backward
in time). Test protocol:

1. Inject a pre-existing watermark file at `<watermark_dir>/<org_slug>/<sensor_id>`
   containing a known timestamp T₀.
2. Run the monitoring-loop stub against a dataset whose event `_time` values are ALL
   OLDER than T₀ (i.e. the "regressing run" scenario — processed events have earlier
   timestamps than the stored watermark).
3. Assert that the post-run watermark written to disk is ≥ T₀ (the run clamps to the
   prior watermark rather than regressing).

A paired positive control: run with events whose `_time` values are NEWER than T₀;
assert post-run watermark > T₀.

(VP-SKILL-050 — watermark monotonicity PRIMARY leg; first-run lookback is VP-SKILL-072;
future-timestamp rejection is VP-SKILL-050 future leg in AC-003; verification-delta vd:756)

### Concurrency Lock Guard

### AC-014 (traces to BC-10.01.001 EC-004 — advisory lock directory (mkdir-based): concurrent invocation exits 0)
When the monitoring-loop's advisory lock directory (mkdir-based) already exists (another instance is running),
the second invocation MUST:
- Log "another instance is running; exiting" to stderr
- Exit 0 (not an error — cron must not alarm on normal single-instance serialization)
- NOT write or modify the watermark
- NOT advance any pipeline stage
Test: pre-create the lock directory (using mkdir), then assert the second invocation exits 0 with the
expected stderr message and no watermark change.
(BC-10.01.001 EC-004 — advisory lock guard; R-003 double-processing prevention)

### AC-015 (traces to BC-10.01.001 EC-005 — advisory lock directory (mkdir-based): stale lock reclaim)
When the advisory lock directory (mkdir-based) exists but its mtime is older than 60 minutes (indicating
a prior crashed run), the loop MUST:
- Remove the stale lock directory (`rm -rf`)
- Acquire a fresh advisory lock directory (`mkdir`)
- Log WATERMARK_STALE_LOCK to STDERR (`echo "WATERMARK_STALE_LOCK: removing stale lock" >&2`;
  arch-delta §D-DEC-002 ~L763). WATERMARK_STALE_LOCK is NOT written to `markers/audit.log`
  (that log records only the 5 Gate-2 hook-enforcement codes: HARD-FLOOR-LIVELOCK-ABORT,
  HARD-FLOOR-UNBINDABLE, UNDER-LABEL-DENIED, SEVERITY-MISMATCH, MARKER-WRITE-FAILED).
- Proceed normally (pipeline continues after reclaim)
Test: create a lock directory with mtime 61+ minutes in the past; assert the loop proceeds
(does not exit early), logs WATERMARK_STALE_LOCK to STDERR (not to `markers/audit.log`),
and processes the expected alerts.
(BC-10.01.001 EC-005 — stale lock reclaim; arch-delta §D-DEC-002 ~L763)
