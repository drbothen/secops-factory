# S-4.02: Delta — assess-priority Skill scored_priority Producer/Consumer Coherence (BC-4.05.001 v1.4)

## Narrative

- **As a** monitoring-loop Stage 5 component
- **I want** the assess-priority skill to expose its output as `scored_priority`
  (ICD-203 verdict field 18) with explicit producer/consumer coherence, including
  `SEVERITY_TO_SCORED_PRIORITY_MAP` on the known-FP fast-path
- **So that** the monitoring-loop hard-floor check (which keys on field 18) and
  disposition-guard (which reads `scored_priority` for severity floor) receive a
  consistent, correctly-typed priority value

## Acceptance Criteria

### AC-001 (traces to BC-4.05.001 invariant 5 — priority IS scored_priority, P12-004)
The `priority` output field of assess-priority IS verdict field 18 `scored_priority`.
These are the same field accessed under two names. The skill must write its result
to the `scored_priority` key in the verdict JSON (field 18). Any code that reads
`priority` and any code that reads `scored_priority` (field 18) must receive the
same value. (P12-004 producer/consumer coherence)

### AC-002 (traces to BC-4.05.001 invariant 5 — SCORED_PRIORITY_ENUM values)
The `scored_priority` field must use the `SCORED_PRIORITY_ENUM` = {CRIT, HIGH, MED,
LOW}. These are four distinct values. The field MUST NOT use SEVERITY_ENUM values
(LOW, MEDIUM, HIGH, CRITICAL) — the naming differs: MEDIUM vs MED,
CRITICAL vs CRIT. Mixing enums is a defect.

### AC-003 (traces to BC-4.05.001 invariant 5 — SEVERITY_TO_SCORED_PRIORITY_MAP)
On the known-FP fast-path, the skill uses `SEVERITY_TO_SCORED_PRIORITY_MAP`:
CRITICAL → CRIT, HIGH → HIGH, MEDIUM → MED, LOW → LOW. This map bridges
SEVERITY_ENUM (detector-native) to SCORED_PRIORITY_ENUM (verdict field 18).
The map must be applied correctly; MEDIUM → MED (not MEDIUM → MEDIUM or
MEDIUM → HIGH).

### AC-004 (traces to BC-4.05.001 invariant — monitoring-loop hard-floor keys on field 18)
The monitoring-loop (S-10.01) reads `verdict.scored_priority` (field 18) for
hard-floor checks. The assess-priority skill produces this value. If the skill
writes `priority` but not `scored_priority`, the monitoring-loop hard-floor check
silently reads nil — defect. The skill MUST write `scored_priority` as the
canonical key.

### AC-005 (traces to BC-4.05.001 invariant 5 — P12-004 producer/consumer coherence)
A test that reads the skill output and reads `verdict.scored_priority` (field 18)
from the same verdict JSON must find identical values. This covers the
producer/consumer coherence guarantee of Invariant #5 (P12-004): assess-priority
output = monitoring-loop input for field 18.

### AC-006 (traces to BC-4.05.001 invariant 5 — SCORED_PRIORITY_ENUM producibility, P12-004)
All four `SCORED_PRIORITY_ENUM` values (CRIT, HIGH, MED, LOW) must be producible
by assess-priority. A test vector for each enum value must exist. This covers the
SCORED_PRIORITY_ENUM membership guarantee of Invariant #5 (P12-004): output is
always from {CRIT, HIGH, MED, LOW}.

### AC-007 (traces to BC-4.05.001 invariant — no SEVERITY_ENUM contamination)
`scored_priority` must NEVER contain "MEDIUM" or "CRITICAL" (SEVERITY_ENUM values).
If either appears in the output, it is a defect. The skill must reject or map these
values. A test that submits a CRITICAL input must verify the output is "CRIT".

### AC-008 — VP-SKILL-070 (traces to BC-4.05.001 invariant 4 — PrismQL org_slug scoping, D-DEC-005)
All PrismQL queries issued by assess-priority (PC#5a, PC#5b, PC#5d) must include
an explicit `org_slug` constraint in the WHERE clause (D-DEC-005). Verification:
(a) Static assertion: every PrismQL block in `skills/assess-priority/SKILL.md`
    (PC#5a/5b/5d) carries `WHERE org_slug=`. (b) DTU multi-org behavioral
fixture (org-a/b/c, `--config-dir <tmpdir>`): an org-a assess-priority invocation
returns zero org-b/c rows. (c) Adversarial leg: an unscoped query (no org_slug
clause) is rejected or falls back to degraded mode per Invariant #4. If org_slug
is not available from execution context, all prism-grounded scoring stages are
skipped entirely. (vd:427, BC-4.05.001 Invariant #4)

### AC-009 — VP-SKILL-071 (traces to BC-4.05.001 PC#6 — confidence float→enum consistency, D-DEC-011)
For every `confidence_score` float output, the paired `confidence` enum must match
D-DEC-011 canonical thresholds: `high` iff score ≥ 0.75; `medium` iff
0.40 ≤ score < 0.75; `low` iff score < 0.40. Boundary test vectors required:
0.75 → `high`; 0.749 → `medium`; 0.40 → `medium`; 0.399 → `low`. An inconsistent
pair (e.g., score=0.80 with confidence="low") is invalid and must be rejected. The
`confidence` enum is always one of `{high, medium, low}`, never a float. This is the
producer-side guarantee complementing VP-HOOK-025's disposition-guard enum type-assertion.
(vd:428, BC-4.05.001 PC#6)
