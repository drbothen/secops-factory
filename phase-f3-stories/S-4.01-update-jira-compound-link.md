# S-4.01: Delta — update-jira Skill Compound Create+Link and Orphan-Link Recovery (BC-4.02.001 v1.21)

## Narrative

- **As a** monitoring-loop verdict executor
- **I want** the update-jira skill to implement rule-2 create+link (PC#7b/D-022/D-024),
  orphan-link recovery (D-026), and SAVE-ALWAYS-SUCCEEDS for markdown path (D-029)
- **So that** when the verdict demands creating a ticket AND linking it to an existing
  one, the link is never written before the create confirms a valid NEW_KEY, and
  markdown-path saves always produce review markers

## Acceptance Criteria

### Rule-2 Create+Link (D-022, D-024)

### AC-001 (traces to BC-4.02.001 postcondition PC#7b rule-2 — create+link; VP-HOOK-036 compound-write model)
When verdict rule-2 applies (ticket_action_type = "create" followed by
"link"), the skill must execute `jr issue create` first, wait for the
response, and confirm a valid NEW_KEY is returned before issuing the link
`jr issue link` command. (D-022, D-024 human decision 2026-07-23)
(VP-HOOK-036 — compound two-sequential-verdict-Write; rule-2 create+link; verification-delta vd:627, D-022/SM-65)

### AC-002 (traces to BC-4.02.001 invariant — Iron Law: link after create)
The link verdict (`jr issue link`) MUST NOT be written until `jr issue create`
returns a valid NEW_KEY. Writing the link before the create response is a defect.
If the create call times out or returns an error, the link must NOT be attempted.

### AC-003 (traces to BC-4.02.001 invariant — anti-fungibility: create marker ≠ link marker)
The create marker and the link marker are not interchangeable. Two separate markers
are required: one for the create action and one for the link action. A single
marker must not authorize both actions. (D-DEC-001)

### AC-004 (traces to BC-4.02.001 postcondition PC#7d — rule-4 create+link)
PC#7d (Closed-ticket create+link, rule-4) also follows the same create-first,
link-after-NEW_KEY Iron Law. The delta applies to both PC#7b (rule-2) and
PC#7d (rule-4).

### Orphan-Link Recovery (D-026)

### AC-005 (traces to BC-10.01.001 EC-010 / D-026 orphan-link executor role; VP-HOOK-036 orphan-link execution leg)
When update-jira receives a link-only verdict issued by the monitoring loop under
D-026 orphan-link recovery (`ticket_action_type=link`, `ticket_id=O`,
`link_target_ticket_id=C`), it MUST execute `jr issue link O C` idempotently.
The skill MUST NOT create a new ticket and MUST NOT issue a comment on O. This
execution path fires when the monitoring loop (S-10.01 AC-020b) has detected open
orphan ticket O lacking the `Relates(O,C)` structural link to Closed ticket C and
issued the corrective link-only verdict. Update-jira's role is pure execution — D-026
detection and verdict emission are entirely the monitoring loop's responsibility.
(VP-HOOK-036 — D-026 orphan-link execution; verification-delta vd:627, SM-68)

### AC-006 (traces to BC-10.01.001 / D-026 orphan-link — idempotency guard; VP-HOOK-036 SM-68 negative/idempotent control)
The orphan-link execution (AC-005) MUST be idempotent: if the `Relates(O,C)` link
already exists in Jira (i.e., a prior recovery run succeeded), re-issuing
`jr issue link O C` MUST NOT create a duplicate Relates edge. A BATS test MUST assert
that running the link command a second time against an already-linked O/C pair
produces no additional link.

This is the **SM-68 negative/idempotent control** (link-PRESENT leg at the EXECUTOR):
it confirms that when `Relates(O,C)` already exists, `jr issue link` is a no-op at the
Jira/DTU level — it does NOT kill SM-68 (whose kill vector is the recovery-fires leg,
owned by S-10.01 AC-020b).

NOTE: the SM-68 KILL is at S-10.01 AC-020b (monitoring loop detects orphan + issues
link-only verdict — recovery fires). Update-jira's role is pure EXECUTION; the idempotency
guard here is the negative/safe-re-run control, not the recovery-firing kill vector.
NOTE: SM-71 kill (d-026-link-read-predicate-skipped-or-inverted, D-026/P21-006) is a
LOOP-level kill owned by S-10.01 AC-020c — SM-71 targets the monitoring-loop D-026
predicate (loop over-fires → duplicate link-only verdict emitted), NOT update-jira's
executor idempotency. This AC is the SM-68 negative control ONLY.
(VP-HOOK-036 — D-026 orphan-link execution idempotency; SM-68 negative control only;
verification-delta ~L1343)

### SAVE-ALWAYS-SUCCEEDS Markdown Path (D-029)

### AC-007 (traces to BC-4.02.001 postcondition PC#4 — D-029 markdown path)
When the verdict write is via the MARKDOWN_REVIEW_PATH, the update-jira skill
treats it as SAVE-ALWAYS-SUCCEEDS: the markdown save always succeeds (Write tool
always succeeds on markdown path), and routing to review is triggered by the
disposition + hard_floor_triggered fields, not by the save result. (P25-001)

### AC-008 (traces to BC-4.02.001 postcondition — regression: normal create/comment/assign unchanged)
Existing AC paths for create, comment, assign, close actions must continue to
operate correctly after this delta. The delta adds new rule-2/rule-4/orphan paths
but must not break existing authorized verdict paths.

### Never-Auto-Reopen (VP-SKILL-066)

### AC-009 — VP-SKILL-066 (traces to BC-4.02.001 invariant 4 — never-auto-reopen on the update-jira path; verification-delta vd:772)
On the update-jira skill path, NO code path from a Resolved (PC#7c) or Closed (PC#7d)
ticket branch may result in a `jr issue move` that transitions a ticket out of its
terminal state (Resolved or Closed). Specifically:

**(EC-007 — Resolved ticket):** When the verdict targets a Resolved ticket, the skill
MUST: (a) draft a propose-only comment with a human-readable SLA statement, (b) halt
further Jira action, and (c) issue zero `jr issue move` reopen commands (i.e. no
`jr issue move <key> <open-state>`).

**(EC-008 — Closed ticket):** When the verdict targets a Closed ticket, the skill MUST:
create a new ticket (`jr issue create`) and link it (`jr issue link`) to the Closed
ticket — it MUST NOT reopen the Closed ticket via `jr issue move`.

**(Static grep vector):** `update-jira/SKILL.md` (and any helper scripts) must contain
no autonomous `jr issue move` command pattern that transitions a Resolved/Closed ticket
to an open/non-terminal state.

(VP-SKILL-066 — update-jira never-auto-reopen; BC-4.02.001 v1.21 Inv#4, §3.4 PC#7c/PC#7d;
paired mutant SM-26 reopen-guard-removed; verification-delta vd:772)

### SLA Surface Never Assume (VP-SKILL-067)

### AC-010 — VP-SKILL-067 (traces to BC-4.02.001 invariant 5 — SLA surface-never-assume; verification-delta vd:773)
The update-jira skill must emit an explicit SLA-impact statement before executing or
proposing any of the following actions: append-comment (PC#7a), link-related (PC#7b),
and propose-reopen (PC#7c). Five required behaviors:

1. **Append-comment path:** output contains "SLA impact:" with the deadline when
   `jr issue view` returns an SLA deadline field.
2. **Link path:** output contains "SLA impact:" annotation before the link action.
3. **Propose-reopen path:** output contains "SLA impact:" with the deadline (or the
   unknown-SLA statement) before drafting the reopen proposal.
4. **SLA data unretrievable:** when `jr issue view` does not return retrievable SLA
   data, the statement reads exactly "SLA: unknown — do not assume compliant" (never
   silently assumes SLA compliance).
5. **Static format grep:** `update-jira/SKILL.md` documents the SLA-statement format
   as an Iron Law or Red Flag; the format string is present in the skill file.

(VP-SKILL-067 — SLA surface-never-assume; BC-4.02.001 v1.21 Inv#5, §3.5;
verification-delta vd:773)
